Key request paths

  1. 1Web UI: browser → Static Web App over HTTPS. The SWA routes /api requests to its linked Function App backend.
  2. 2Function data: Function App → outbound VNet integration → log storage Table private endpoint → applogs. VNet-linked private DNS resolves the Table hostname.
  3. 3External ingest: allowed caller IP (e.g. AWS) + function key → ingest Function App → VNet integration → log storage Table private endpoint. Other source IPs are denied; the UAMI authorizes the write.
  4. 4Function platform storage: the Function App uses private Blob, Queue, and Table endpoints for host and deployment storage.
  5. 5Retention: a daily timer in the ingest Function App deletes records older than retentionDays from the log table.
  6. 6Observability: Function telemetry → Application Insights → Log Analytics.

Boundary & access notes

VNet: Contains the Function integration subnet and private endpoints, not the Function App or Storage accounts themselves. Storage accounts have public network access disabled; they are reachable only through private endpoints.

SWA: The deployed inventory has no SWA private endpoint. The portal’s Private Endpoints pane is a configuration surface; it does not indicate one is active.

Function ingress: the Function origin remains network-public, as required by the SWA linked-backend integration. That integration provides SWA-exclusive API access when no other Function authentication policy is configured. Do not add Function IP restrictions, service endpoints, or Private Link while this backend link is in use. SWA routes require an authenticated user for both site content and API requests; unauthenticated requests are redirected to Microsoft Entra sign-in before content or data is returned.

NSGs: Both subnet NSGs exist, but no custom security rules are defined in the IaC.
